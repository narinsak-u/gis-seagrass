# Physical Backend Layers

The backend uses explicit physical layers, not only file-name conventions: each feature owns `http`, `application`, `domain`, and `infrastructure`; platform concerns and import orchestration have their own modules. Application and domain code remain framework- and database-independent, with dependency direction enforced by a lightweight architecture check. Site–Survey coordination stays in a dedicated application/composition module and passes an opaque transaction context through ports, so feature modules share one Drizzle transaction without importing one another's infrastructure. The composition module binds feature-owned adapters to those ports; separate Nest modules used only for infrastructure provider registration are unnecessary. External feature callers use public application contracts, while the CLI composes the same adapters in its own infrastructure entrypoint. This keeps adapter ownership clear without duplicate module wrappers; existing API, database, spatial, and concurrency behavior remains unchanged.
